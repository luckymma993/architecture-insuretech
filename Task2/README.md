# Задание 2. Динамическое масштабирование

## Файлы

| Файл | Содержимое |
|------|-----------|
| `deployment.yaml` | Deployment: 1 реплика, лимит памяти 30Mi, порт 8080 |
| `service.yaml` | Service типа NodePort на порт 8080 |
| `hpa.yaml` | HPA: масштабирование по памяти, цель 80%, от 1 до 10 реплик |
| `locustfile.py` | Сценарий нагрузки: пользователи ходят на `GET /` с паузой 1–5 с |
| `replicas-log.txt` | Состояние HPA и Deployment каждые 15 секунд во время теста |
| `hpa-describe.txt` | Вывод `kubectl describe hpa` с событием `SuccessfulRescale` и список подов |

## Запуск

```bash
minikube start -p sprint8 --driver=docker --cpus=2 --memory=2048
minikube -p sprint8 addons enable metrics-server
kubectl apply -f deployment.yaml -f service.yaml -f hpa.yaml
minikube service scaletestapp -p sprint8 --url
locust -f locustfile.py --headless -u 300 -r 30 -t 5m --host <адрес из предыдущей команды>
kubectl get hpa scaletestapp --watch
```

## Почему в Deployment указан requests.memory

HPA с типом `Utilization` считает загрузку как отношение фактического потребления к `requests`, а не к `limits`. Без `requests.memory` HPA не может посчитать процент и не масштабирует. Лимит 30Mi из задания сохранён.

Запрос 15Mi выбран по замерам приложения: в простое оно занимает около 7–8Mi, под нагрузкой около 14Mi (`process_resident_memory_bytes`). При запросе 20Mi под нагрузкой было около 72% и порог 80% не достигался. При 15Mi порог достижим, а потребление в простое остаётся около 50%.

Порог 80% поэтому означает 12Mi на под, а не 24Mi от лимита.

## Результат теста

Нагрузка: 300 пользователей, по 30 новых в секунду, 5 минут, `GET /` через Service (`minikube service --url`).

| Показатель | Значение |
|-----------|----------|
| Запросов | 28 984, ошибок 0 |
| Средняя скорость | около 97 запросов в секунду |
| Время ответа | среднее 60 мс, медиана 64 мс, максимум 226 мс |

Ход масштабирования (`replicas-log.txt`):

- 15:53:43 – 15:54:13: память 10%, реплик 1.
- 15:54:29: память растёт до 79%, 88%, затем 94% к 15:56:32.
- 15:56:32: HPA добавляет вторую реплику (`SuccessfulRescale: New size: 2`).
- После этого память на под падает до 52–55%, число реплик остаётся 2.

Рост получился до двух реплик: нагрузки хватило, чтобы пересечь порог, но не до максимума в 10.

Нагрузка шла через `minikube service --url`, а не через `kubectl port-forward`: port-forward направляет весь трафик в один под и не показывает распределения по репликам.
